## 一、问题定义（编译原理视角）

CK3 脚本是一棵树，每个位置有一个**隐式类型**——作用域（scope）。
trigger / effect 都是**带作用域前置条件的函数**：

```
has_realm_law : character → bool        （script_docs: scopes = ["character"]）
any_vassal    : character → bool        且块内作用域切换为 character
liege         : character → character   （文档未给，需推断）
```

所以「脚本报错」中有很大一类是**类型错误**：

```
[E][jomini_trigger.cpp]: Scope mismatch
Error: has_realm_law trigger [Failed context switch]
```

**这和类型检查器要解决的问题是同一个**：

| 编译器概念 | CK3 对应物 |
|---|---|
| 类型 | scope type（`character` / `landed_title` / `faith` …） |
| 类型环境 | 当前的 `scope:` 与 saved scope 表 |
| 函数签名 | `trigger/effect` 的 `scopes[]` |
| 作用域绑定（λ） | `liege = { … }` / `any_vassal = { … }` |
| 多态 | `scripted_trigger` / `scripted_effect`（无声明，随调用点变） |
| 动态类型 | `set_variable` 存取 scope、`scope:x` 来自事件 |
| 类型错误 | Failed context switch / PostValidate false |

1. **作用域链路的类型**（`liege` 从什么到什么）
2. **每种块的根作用域**（`law.can_keep` 的 root 是什么）

## 三、核心思路：从良构语料反推类型环境

**不去问文档，去问本体脚本。** 本体是自洽的（P 社自己跑得起来），
所以**本体脚本里的每一次合法调用都是一条类型约束**。

### 3.1 已实测验证

对本体 `common/laws` 的 102 个 `can_keep` 块，收集其中调用的已知 trigger，
对它们的 `scopes[]` 求交集：

```
100 个 → [character]     ← 与 _laws.info 的「Root scope = ruler」完全一致
  2 个 → [faith]        ← 原型未跟进的嵌套 scope 切换，属可解释的误判
```

**100/102 命中，2 个异常可解释。** 思路成立。

### 3.2 形式化

设 `T(s)` 为符号 `s` 在位置 `p` 的作用域类型集合。

**约束生成**：
- 若块 `B`（类型 `β`）里出现了 trigger `t`，且 `t.scopes ≠ ∅`
  ⇒ `root(β) ⊆ t.scopes`
- 若 link `L = { … }` 里出现了 trigger `t`
  ⇒ `result(L) ⊆ t.scopes`
- 若 `any_X = { … }`，`X.targets = [τ]` ⇒ 块内作用域 `= τ`

**求解**：对每个未知量取所有约束的**交集**。
交集为空 ⇒ 该块/链路本身不自洽（本体 bug，或我们用错了），记录下来人工看。

## 四、类型系统设计

### 4.1 类型域

```
τ ::= 作用域类型名的有限集合             （may-set，表示「可能是这些之一」）
    | ANY                               （未知，永不报错）
    | ⊥                                 （空集，必然出错）
```

CK3 的 scope 类型是**平铺的**（无继承），所以不需要子类型判定，只要集合交/并。

### 4.2 判定规则

| 语法 | 当前作用域如何变化 |
|---|---|
| `t = X` （trigger，`scopes` 非空） | 检查 `当前 ⊆ scopes`，不改变 |
| `X = { … }` 其中 X 是迭代器 | 子块作用域 = X 的 `targets` |
| `link = { … }`，link 是普通 event_target | 子块作用域 = `result(link)`（推断） |
| `scope:x = { … }` | 子块作用域 = 绑定表里 x 的类型，未知则 ANY |
| `if / else_if / while / custom_tooltip / custom_description` | 不变 |
| `save_scope_as = x` | 记录 `x ↦ 当前作用域` |
| `save_temporary_scope_as = x` | 同上（局部） |
| `exists = X` | 只检查 X 可解析 |

### 4.3 报告策略：宁可漏报，不可误报

**只有确定才报 error**：
- 当前作用域 ≠ ANY，且与 `scopes` 无交集 → `error(scope)`
- 当前作用域 = ANY 或有交集 → 不报

理由：tiger 那 74 条误报的教训——**误报会让工具失去可信度**。

## 五、分阶段计划

### Phase 0：作用域类型代数（0.5 天）

- 从 `symbols-ck3.json` 提取 scope 类型名全集（约 30 个）
- 定义集合运算与 ANY/⊥ 的处理
- **产出**：`scope_types.json`
- **验收**：`has_realm_law`/`any_vassal` 的 scopes/targets 能正确读出

### Phase 1：环境推断（2–3 天，离线跑一次）

| 子任务 | 内容 |
|---|---|
| 1.1 | 块类型 → 根作用域（用 §3.2 的交集法，扫全部 `common/`） |
| 1.2 | event_target → 结果类型（扫全部 `common/` + `events/`） |
| 1.3 | saved scope 传播（块内 `save_scope_as` → 后续 `scope:x`） |
| 1.4 | 迭代器 targets（已有数据，直接读） |

**产出**：`scope-env-ck3.json`

```json
{
  "block_roots": { "law.can_keep": ["character"], "law.modifier": ["character"], ... },
  "channel_types": { "liege": ["character"], "primary_title": ["landed_title"], ... },
  "confidence": { "law.can_keep": {"observations": 102, "agreement": 1.0} }
}
```

**验收**：抽 20 条人工核对，要求 ≥18 条正确。
已知答案样本：`liege→character`、`primary_title→landed_title`、
`capital_province→province`、`faith→faith`、`law.can_keep→character`。

**⚠️ 止损点**：若 agreement < 0.8，说明交集法被嵌套作用域干扰太严重，
先补「嵌套感知」再继续，不要带病往下做。

### Phase 2：检查器（3–4 天）

- 输入：脚本文件 + 根作用域（从 `block_roots` 查）
- 递归下降，维护作用域环境
- **产出**：`check_scopes.py <file-or-dir>`
- **验收**：对本体自身跑，误报率应 < 5%；对已知坏样本（TAO）应能抓到真实错误

### Phase 3：集成（1–2 天）

- 依赖索引的边加作用域标注
- 新查询：`who <sym> --scope character` → 只看某作用域下的调用
- 新查询：`mismatch` → 列出「调用点作用域 ∉ 符号 scopes」的边
- 合并进 `query_deps.py`

## 五·五、致命前提：**本体不是真理基线**

### 证据

社区维护的 `Unofficial Patch`（workshop 2871648329）：

- **1,416 个 `#Unop` 修复标记，分布在 347 个文件**
- `README`：**CK3 1.20 一次性吸收了约 2,550 条社区修复**
  （`#Unop` 标记从 ~3,900 降到 ~1,416，修改文件从 ~550 降到 ~347）
- 仍有大量未修，且每个新版本还会引入新的

### 对本设计的影响（必须正面回答）

**§3 的「从语料反推类型环境」会继承本体的 bug。**

如果某处本体脚本本身就写错了作用域，我们就会学到一条错误的约束，
然后用它去误判正确的 mod 代码。

> **这会直接摧毁工具的可信度——而「不误报」是本设计的首要原则。**

### 缓解措施（三条，缺一不可）

> 具体权重的取值与仲裁规则见 **`../机制结论/来源权重与仲裁.md`**（社区 0.95 / 引擎 0.80 / 语料 0.60 / 别的 mod 0.30）。

**① 建立不可信区域黑名单**

```bash
# 扫 Unofficial Patch 的 #Unop 标记 → vanilla-bugs.json
# 从这些行所在的块推断约束时，标记为低置信度
```

`#Unop` 标记是**现成的人工标注集**，等于社区已经替我们标好了
「P 社这里写错了」。它的价值比我们自己去猜高得多。

**② 交集为空 = 可疑，交人工复核**

求解时若某块所有约束的交集为 `⊥`，大概率是：
- 本体该块有 bug，或
- 我们的嵌套感知不对

**两种情况都不能自动下结论**，进人工队列。

**③ 每个推断结果都带置信度**

```json
{ "law.can_keep": { "scope": ["character"], "observations": 102,
                    "agreement": 1.0, "unop_marked": 0 } }
```

`agreement` 低或 `unop_marked` 高的条目，查询时显式提示「此结论参考价值有限」。

### 一句话原则

> **文档和本体都只是「权威性较高的参考」，不是真理。
> 工具的价值在于「缩小怀疑范围」，不在于「给出判决」。**

这条同样适用于 `symbols-ck3.json`——它是游戏自己打印的，
如果引擎的声明本身有错，它也跟着错。

## 六、难点与取舍（诚实列出）

| 难点 | 影响 | 取舍 |
|---|---|---|
| **多态**：`scripted_trigger` 无声明 | 同一 trigger 在不同作用域被调 | 逐调用点特化（monomorphize）；只报「所有调用点都失败」 |
| **动态变量**：`set_variable` 存 scope | 类型不可静态确定 | 一律 ANY，永不报 |
| **`scope:x` 来自事件** | `scope:actor` 等由事件类型决定 | 用 `event_scope` 名字兜底为 ANY；不做跨事件推断 |
| **根作用域覆盖率** | 有些块推断不出（样本太少） | 覆盖不到就跳过，不猜 |
| **嵌套作用域干扰** | 原型里那 2/102 的 `faith` | Phase 1 必须做嵌套感知，否则 agreement 下降 |
| **本体自身可能有 bug** | 学到错误的约束（见五·五） | `#Unop` 黑名单 + 交集为空入队列 + 结果带置信度 |

## 七、MVP（最小可用，建议先做这个）

**只覆盖一类块 + 一类链路**，验证价值后再铺开：

- 块：`common/laws` 的 `can_keep` / `can_pass` / `potential`
- 链路：`liege` / `primary_title` / `scope:x`
- 检查：这两个块里调用 trigger 时作用域是否匹配

**能覆盖今天这类问题**（法令写对了但不生效），
工作量约 1–2 天，且不需要完整环境推断（`can_keep` 的根作用域已知是 character）。

**判据**：MVP 能不能抓到 TAO 里的一个真实错误？
能，才值得做 Phase 1 全量推断；不能，说明方向还需调整。

## 八、与现有工具的分工

| 工具 | 回答什么 | 覆盖 |
|---|---|---|
| `symbols-ck3.json` | 这个符号存不存在、要什么作用域 | 引擎内置 |
| `deps-ck3.json` | 这个符号被谁用、依赖谁 | 脚本定义之间 |
| **scope checker（本设计）** | **这个调用点的作用域对不对** | **上下文相关** |
| `ck3-tiger` | 综合静态检查 | 全量，但误报多 |

**四者是互补的：tiger 告诉你「可能有问题」，scope checker 要告诉你「确定有问题，在哪个作用域下」。**
