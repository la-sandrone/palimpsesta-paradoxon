| 来源 | 权重 | 依据 | 可信边界 |
|---|---|---|---|
| **社区修订**（`#Unop` 等人工标注） | **0.95** | 有人审查过；P 社反复采纳 | 采纳前可能过时；个别修复本身有争议 |
| **引擎自述**（`script_docs` 导出） | **0.80** | 引擎自己的声明 | **声明 ≠ 行为**；未覆盖运行时语义 |

| **其他 mod** | **0.30** | 可能提供思路 | bug 密度极高，只能当线索 |

### 权重是排序值，不是概率

**禁止跨来源做加权平均。** 平均值没有意义，只会造出一个看起来精确的假数字。

正确用法：**冲突时按权重排序，取高者作结论，低者留档。**

### 加载顺序约定（社区实践，也是我们的基准）

用户实际玩法的排序：

```
Unofficial Patch        最前   ← 作为其他 mod 合并的基准
官中修正                 紧跟其后
牛奶の官中修正           再后面（官中修正要求排在奶皇版「上面」）
...其他 mod
```

**这条顺序对工具有直接含义：**

> **「正确基线」不是原版，而是「Unop 打过补丁的原版」。**
> 语料反推（如作用域环境推断）应当跑在补丁后的本体上，
> 而不是原始本体——否则会学进 356 条已知的 scope 错误。

### 牛奶版修订词条的结构价值

`修订词条.txt` 是**逐条记录「原官中 → 改为」**的文本：

```
1、修改官中键值：[b] study_scripture_outcome.150.desc [/b]
『“神殿的田地、磨坊……”』
[b] 改为 [/b]
『“神庙周边的田地、磨坊……”』
```

**这是本地化领域的「社区标注集」**，与 `#Unop` 标记同构：
- 111 条能解析出 loc key
- 6 个日期分节（10.14 / 10.8 / 9.10 / 8.19 / 8.6 / 7.27）

⇒ 可作为本地化工具的**冲突判据**：若某个 mod 的 loc 与官中冲突，
但与牛奶版一致，则倾向判为「修正」而非「错误」（规则 3 的直接应用）。

## 二、仲裁规则

### 规则 1：冲突必须显式记录

```json
{
  "fact": "scope_of(block=law.can_keep)",
  "candidates": [
    {"value": ["character"], "source": "vanilla_corpus", "weight": 0.60, "observations": 100},
    {"value": ["character"], "source": "engine_doc",    "weight": 0.80},
    {"value": ["character"], "source": "community",     "weight": 0.95}
  ],
  "conflict": false,
  "verdict": ["character"]
}
```

**禁止**只输出 `verdict` 而丢掉 `candidates`——那是把证据抹掉，
下次有人质疑时无法复盘。

### 规则 2：社区修订优先于本体

若某处本体写法与社区修订不一致，**以社区修订为准**，
并记录 `"vanilla_suspect": true`。

### 规则 3：检查 mod 时的误报抑制（重要）

> **若 mod 的写法与本体冲突，但与社区修订一致 ⇒ 不报 error，降为 info。**

理由：mod 作者可能正是在修本体的 bug。
我们的工具不该把「修正」判成「错误」。

这一条能直接减少作用域检查器的误报——而误报是本工具最大的失败模式。

### 规则 4：找不到任何来源 ⇒ 输出 unknown，不猜

```json
{"value": null, "reason": "no_source", "confidence": 0}
```

**不猜，比猜错好。**

## 三、各工具如何记录

### `symbols-ck3.json`（引擎自述）

已经是 `source_kind: "script_documentation（游戏自动导出）"`，权重 0.80。
**补一条**：凡是 `community-fixes.json` 里有 `class=scope` 标记的位置，
相关符号的 `scopes` 声明降权，查询时提示「本体此处可疑」。

### `deps-ck3.json`（语料推断）

每条边都是「本体里 A 引用了 B」，这是**事实**（本体确实这么写），权重本身没问题。
**但由边推出的结论**（如「A 依赖 B」）继承本体的正确性，权重 0.60。

### `community-fixes.json`（社区修订）

```json
{
  "file": "...", "line": 307, "class": "scope",
  "note": "Also accept a modded building granting the parameter"
}
```

权重 0.95。**注意它的语义是「本体此处有错」，不是「这样写才对」**
——它记录的是修复**位置**，具体正确写法要读 patch 内容。

### 作用域检查器

- 环境推断结果必须带 `observations` / `agreement` / `unop_marked`
- `unop_marked > 0` 的条目，`agreement` 再高也要降权
- 检查 mod 时套用规则 3

## 四、实测数据（供判断权重是否合理）

`community-fixes.json` 的分类统计：

| 类别 | 条数 | 说明 |
|---|---|---|
| `other` | 892 | 杂项 |
| **`scope`** | **356** | 作用域相关——**直接打在作用域检查器上** |
| `missing` | 60 | 引用不存在的东西 |
| `loc` | 52 | 本地化 |
| `debug` | 25 | 加调试日志 |
| `logic` | 21 | 逻辑恒真/恒假 |
| `ai` | 5 | AI 权重 |

**356 条 scope 类修复意味着**：如果作用域检查器只从本体语料学，
会学到 356 处已知错误的模式。**这就是为什么必须先建好权重框架再建检查器。**

## 五、一句话

> **工具的价值是「缩小怀疑范围」，不是「给出判决」。
> 每个结论都要能回答：这是谁说的？凭什么？**
